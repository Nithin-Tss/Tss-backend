# New table: `analytics.storefront_sessions`

**Purpose.** One row per visit to a store's storefront, so the Analytics page and reports can show sessions,
visitors, conversion rate, landing pages, referrers, devices and countries. It is the only table added; there is
no page-view table, no rollup table and no change to `store_daily_metrics`. Why it is needed: sales analytics can
be rebuilt from orders, but visits exist nowhere else.

**Migration.** `orders.0014_storefront_sessions` (creates one table; the `analytics` schema already exists from `orders.0012`).
`orders.0014_storefront_sessions` only lists "paid" as a referrer type (a Django choice: no SQL, no schema change).

## Columns

| Column | Type | Null | Notes |
|---|---|---|---|
| id | uuid | no | PK, generated by the app |
| store_id | uuid | no | FK `tenancy.stores`, ON DELETE CASCADE (same type as `store_daily_metrics.store_id`) |
| visitor_id | varchar(64) | no | random id kept in the shopper's browser; not a person, not an IP |
| started_at | timestamptz | no | |
| last_seen_at | timestamptz | no | CHECK `>= started_at` |
| landing_path | varchar(255) | no | store-relative path, query string removed; `''` if unknown |
| landing_page_type | varchar(20) | no | home / product / collection / cart / checkout / other |
| referrer_host | varchar(255) | no | host only, no path or query; `''` = none |
| referrer_type | varchar(20) | no | direct / search / social / email / paid / other |
| utm_source, utm_medium, utm_campaign | varchar(100) | no | `''` if absent |
| device_type | varchar(10) | no | desktop / mobile / tablet |
| country | varchar(2) | no | from the `CF-IPCountry` header when present, else `''` |
| page_views | integer | no | CHECK `>= 1`; +1 per page load in the visit |
| added_to_cart, reached_checkout | boolean | no | default false |
| order_id | uuid | yes | FK `orders`, ON DELETE SET NULL; set when an order is placed from the visit's cart |
| cart_session | varchar(64) | no | the shopper's cart id; lets cart/checkout/order events find their visit |
| created_at, updated_at | timestamptz | no | same as `store_daily_metrics` |

No IP address, user agent, email or name is stored. The FKs to `stores` and `orders` have no index of their own.

## Indexes (only what the queries use)

| Index | Used by |
|---|---|
| PK (id) | |
| `idx_sfsession_store_started` (store_id, started_at) | all reports: sessions in a date range per store |
| `idx_sfsession_store_seen` (store_id, last_seen_at) | finding a visit by cart id within the last 24 h (cart/checkout/order events, newest first) |
| `idx_sfsession_store_visitor` (store_id, visitor_id) | finding the visitor's current visit on each page load |

## Write pattern

A visit starts after 30 minutes without activity or a new day in the store's timezone. Per visit: 1 insert, then
1 update per further page load (`page_views`, `last_seen_at`), and up to 3 small updates for the cart/checkout/order
flags. `last_seen_at` is indexed, so those updates are not HOT updates; at the volumes below this is negligible.
Default autovacuum settings are enough.

## Expected size at ~1,000 visits/day (per store)

| | Rows | Approx. size incl. indexes (~0.5 KB/row) |
|---|---|---|
| per day | ~1,000 | ~0.5 MB |
| per month | ~30,000 | ~15 MB |
| per year | ~365,000 | ~180 MB |

Writes: ~1,000 inserts and ~3,000–5,000 updates a day (assuming 3–5 page loads per visit). Reads: report queries
scan one store's date range through `idx_sfsession_store_started`.

## Suggested retention

* Keep raw rows **13 months** (the reports compare with the same dates last year), then delete rows with
  `started_at` older than that, in batches of a few thousand by a scheduled job.
* Not implemented yet: the job is only a suggestion until the database team agrees.
* If a single store or the whole table passes ~50 million rows, partition by month on `started_at`
  and drop old partitions instead of deleting.
* Deleting a store removes its sessions (cascade). Deleting an order keeps the session and clears `order_id`.
